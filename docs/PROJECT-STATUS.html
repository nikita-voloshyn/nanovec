Zero-dependency in-memory vector DB → MCP server for ephemeral agent working memory

v0.1.0 rust stable edition 2021 2026-05-19

NanoVec — это in-memory векторная БД на чистом Rust без сторонних индекс-библиотек (никакого FAISS / HNSWLIB / Annoy), реализованная как MCP-сервер. Цель — sub-millisecond семантический поиск для эфемерной рабочей памяти AI-агентов. Все алгоритмы написаны с нуля: SoA-хранилище, NEON/AVX2 distance-функции, KD-Tree, multi-collection с metadata-фильтрами, BoundedMaxHeap, brute-force KNN. Эта страница фиксирует завершение фаз 1–5: от пустого репо до полноценной векторной БД с sub-линейным поиском и SIMD-ускорением 9–12×.

Архитектура

Что было сделано

Phase 1 — Zero → Working complete

От пустого репо к работающему MCP-серверу с векторным поиском.
  • VectorStore — flat Vec<f32>, SoA layout, dimension locked at init, swap-remove для O(1) удаления
  • RecordStore — Vec<VectorRecord> + HashMap<u64, usize> для O(1) lookup по ID
  • Scalar distance functions: L2 / Euclidean, Cosine, Dot product (все в src/distance/)
  • BoundedMaxHeap — top-K с O(log K) вставкой, основа brute-force search
  • BruteForce::search — линейный скан + heap, поддержка трёх метрик
  • Координированный delete(id) через swap-remove + update_offset
  • MCP-сервер на rmcp (stdio): index_vector, search, delete, stats
  • Базовый proptest-набор для distance-функций, 100% unit-test покрытие core-модулей

Phase 2 — Vectors → Text complete

Клиент шлёт текст, не вектор; embedder работает на сервере.
  • Embedder на candle + sentence-transformers/all-MiniLM-L6-v2 (384 dim, L2-normalized)
  • Pipeline: tokenize → BertModel::forward → mean-pool weighted by attention mask → L2-normalize
  • Модель грузится один раз, mmap-loaded из safetensors (// SAFETY: задокументирован)
  • MCP-инструменты index_document(text, metadata) и search_document(query, k)
  • Exhaustive EmbedError enum: Download / Tokenize / ModelLoad / Inference
  • Интеграционные тесты со stdio transport (полный round-trip JSON-RPC)

Phase 2.5 — Search Ergonomics complete

UX-чистка перед оптимизацией: API должен быть удобен ДО того, как становится быстрее.
  • clear MCP-инструмент: bulk reset обеих сторон (VectorStore::clear + RecordStore::clear) с сохранением dimension lock
  • Expanded stats: default_metric, информация про embedder (MODEL_NAME, dimension)
  • Search results теперь возвращают и distance (raw score), и similarity (нормализованная 0–1)
  • Документация ограничений модели: MiniLM-L6 обучен на английском, слабо работает с другими языками
  • Multilingual Polish test-сценарий + ScootGo-корпус в docs/TEST-CORPUS-MULTILINGUAL.md
  • Bilingual README (en/uk), полная пере-документация компонент в docs/components/

Phase 3 — Scalar → SIMD complete

Векторизация горячего пути дистанций. 9–12× ускорение на M1 NEON.
  • src/simd/ с диспетчером, переключающим бэкенды по cfg(target_arch = ...)
  • simd/neon.rs — aarch64: vfmaq_f32 + vaddvq_f32, 4-кратный анролл (16 lanes/iter) + 4-lane хвост + scalar remainder
  • simd/avx2.rs — x86_64: _mm256_fmadd_ps + horizontal reduce, 4-кратный анролл (32 lanes/iter), runtime is_x86_feature_detected!
  • simd/scalar.rs — единственный источник правды для scalar fallback (старая реализация переехала сюда)
  • Public API nanovec::distance::* сохранён без изменений — внутри теперь делегирует в SIMD
  • Все unsafe-блоки задокументированы // SAFETY: комментариями (длина, target-feature, границы указателей)
  • Proptest: SIMD vs scalar на векторах длиной 1..=2048, epsilon = 1e-3

Phase 4 — Pile → Organized complete

Multi-collection storage + metadata-фильтр перед distance-петлёй.
  • src/store/collections.rs: CollectionMap с HashMap<String, Collection>, exhaustive CollectionError
  • Lazy "default" collection — backwards compat: старые MCP-запросы без collection работают как раньше
  • BruteForce::search получил параметр filter: Option<&[(String, String)]> — AND-семантика, pre-prune ДО distance computation
  • Новые MCP-инструменты: create_collection, list_collections, drop_collection
  • Existing tools получили optional collection и filter поля
  • stats теперь репортит per-collection counts + aggregate, сохраняя legacy top-level fields
  • Integration test tests/integration/mcp_collections.rs — полный round-trip multi-collection + filter через stdio JSON-RPC

Phase 5 — O(n) → O(log n) complete

KD-Tree spatial index с геометрическим pruning. 26× speedup на низких размерностях.
  • src/index/kdtree.rs: flat Vec<KdNode> layout (без Box<Node> recursion), DFS-order ноды, child indices как u32
  • KdTree::build — O(n log n) через select_nth_unstable_by, splitting axis = depth % dim
  • KdTree::search — backtracking с |delta| pruning (Euclidean only), pruning radius из BoundedMaxHeap::peek_worst
  • Filter работает: записи, не прошедшие фильтр, не попадают в heap (документировано как pruning-aware limitation)
  • should_use_kdtree(n, dim) heuristic: n >= 1024 && dim <= 64 — за пределами этой зоны brute-force выигрывает из-за curse of dimensionality
  • Immutable после build (insert/delete требуют rebuild — документировано)
  • Proptest kdtree_matches_brute_force на 2D/4D/8D, 64 случая каждая размерность — KdTree и BruteForce возвращают идентичный список ID

Benchmark baseline

Все замеры — на Apple M1 Pro (10 cores, arm64), cargo bench в release-профиле. Это скалярная точка отсчёта: Phase 3 заменит горячие пути на SIMD (AVX2/NEON/portable_simd), и эти таблицы станут «до». Цифры — медианные значения из 100 выборок (criterion).

Как читать: для дистанций интересна не только секунда-в-секунду цифра, а throughput в Gelem/s (миллиардов элементов вектора в секунду). Cosine в ~3× медленнее dot/L2 из-за двух дополнительных квадратов норм и одного sqrt — это и есть главная цель SIMD.

KD-Tree vs Brute-force · K=10

Геометрический pruning работает на низких размерностях — на dim=8 при 10k векторов выигрыш 26×. На dim=384 «преимущество» 7.5× обманчиво: бенч-корпус синтетический (sin-кластеризован); на embedding-вектор не переносится. Документация и should_use_kdtree об этом предупреждают.

SetupBruteForceKdTree::searchSpeedupBuild cost
dim=8 · N=1 000 5.83 µs 2.02 µs 2.9× 138 µs
dim=8 · N=10 000 39.4 µs 1.47 µs 26.8× 2.51 ms
dim=384 · N=1 000 40.8 µs 17.0 µs 2.4× — *
dim=384 · N=10 000413.2 µs 54.8 µs 7.5× — *

* На реальных embedding'ах MiniLM при dim=384 pruning почти не работает — используй BruteForce + SIMD.

Sanity check: для агентской рабочей памяти (10K векторов, top-K=10) дешёвый метрик-выбор уже даёт sub-3ms latency без всякой акселерации. Это значит, что MVP-цель «sub-millisecond» достижима для корпусов до ~3K векторов прямо сейчас, а SIMD-ускорение на M1 NEON должно вывести 10K в эту зону.

BoundedMaxHeap · top-K eviction patterns

«Random» — типичный случай (случайные score). «Adversarial» — score монотонно убывает, каждая вставка после заполнения heap'а вытесняет вершину; верхняя граница стоимости.

PatternN · K=1N · K=10N · K=50
random · N=1 000 3.60 µs 3.71 µs 4.57 µs
random · N=10 000 35.8 µs 35.9 µs 37.4 µs
adversarial · N=1 000 4.71 µs 8.95 µs 15.96 µs
adversarial · N=10 00046.2 µs 84.5 µs 241.4 µs
Где боль: в adversarial-режиме при N=10K, K=50 heap «съедает» 241 µs — это ~10% от общего search time для L2 (2.67 ms). После SIMD-ускорения дистанций доля heap'а вырастет; на Phase 4/5 имеет смысл рассмотреть quickselect-вариант для больших K.
